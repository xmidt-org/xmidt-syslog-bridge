# A failing destination pauses consumption, it does not fail the process

When a write to the **Destination** fails for a transient reason, xmidt-syslog-bridge stops fetching from the **Event Source** and retries that write with backoff until it succeeds. The behavior is identical for the **Syslog Destination** and the **S3 Destination**, so there is one retry-and-backoff component rather than one per destination. Not committing the offset is necessary but not sufficient: a consumer that keeps fetching while it cannot write accumulates fetched records in memory for the length of the outage, and since ADR 0001 gives us no spool to put them in, that ends in an out-of-memory restart loop. Pausing the fetch is what makes the source actually serve as the buffer.

This makes a destination outage a normal, survivable operating state rather than a fault, which has a consequence for health checks: **liveness must not depend on destination reachability**. During an S3 or rsyslog outage every instance in the consumer group is equally unable to write, so a health endpoint that reported unhealthy would have Kubernetes kill and restart all of them, adding a rebalance storm to an outage that no restart can fix. Liveness reports only that the process is up and its consume loop is not wedged. Destination trouble surfaces through metrics — write errors by reason, time since last successful write, and consumer lag — which page a human instead of tripping a kill switch. Adding a destination probe to the health endpoint looks like an improvement and is not; that is why this is written down.
